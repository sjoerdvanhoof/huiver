# huiver

Drop in an ebook, get back an audiobook — a collection of tagged MP3s, one per chapter.

Speech is generated by [Kokoro-82M](https://huggingface.co/hexgrad/Kokoro-82M) running
locally on your machine. Nothing is uploaded anywhere.

**Input formats:** `.epub` (or a zipped one), `.txt`, `.md`, `.html`

Files are identified by their contents, not their name — so a `book.epub.zip`, or an
unpacked `.epub` folder that your browser compressed on the way in, both work.

## Setup

Requires [Bun](https://bun.com), Python 3.11, `ffmpeg` and `espeak-ng`.

```bash
brew install python@3.11 ffmpeg espeak-ng
bun install
bun run setup:python     # creates .venv and installs kokoro + torch (~1 GB)
```

## Sample books

```bash
bun run examples
```

Downloads 10 public-domain EPUBs from Project Gutenberg into `examples/` (gitignored)
and adds them to your library. Reload the page and they're on the shelf.

Start with **The Yellow Wallpaper** — at ~51k characters a full conversion takes a
couple of minutes instead of hours. See `examples/README.md`.

Already have files in `examples/`? `bun run examples:import` shelves them without
re-downloading. Both are safe to run while `bun dev` is up, and skip books already
imported.

## Run

```bash
bun dev
```

Then open http://localhost:3000, drop a book onto the library panel, pick a voice and
hit convert. The first conversion downloads the Kokoro model (~350 MB); after that it
runs entirely offline.

Generated audio lands in `data/audio/<jobId>/` as `001-chapter-title.mp3`, tagged with
title/album/artist/track so it imports cleanly into a podcast or audiobook player. You
can also grab everything as a zip from the job panel.

### Voice previews

Every voice in the dropdown has a play button that speaks a sample line. The first
preview of a voice takes a few seconds to render; after that it is cached on disk in
`data/previews/` and plays instantly.

### Listen now (live streaming)

The play button on a chapter row streams it as it is being generated, so audio starts
after the first short chunk (a second or two) instead of after the whole chapter.

Kokoro renders around 5x faster than realtime on Apple silicon, so playback stays
comfortably ahead. If your machine is short on RAM the model will swap and throughput
can drop below realtime, which makes long chapters stutter — convert them instead.

Each worker holds about 1 GB of weights. One is kept warm for 5 minutes between
previews and streams, then retired; it also exits on its own if it is ever orphaned.

## GPU

Kokoro's own device auto-detection only looks for CUDA, so on a Mac it silently runs
on the CPU. huiver picks the device itself and prefers Apple Silicon's GPU (MPS).

Measured on an M1 Air, same text, same voice:

| Device | Speed | vs realtime |
| --- | --- | --- |
| CPU | 4.50s per 24.4s of audio | 5.4× |
| MPS | 3.14s per 24.4s of audio | 7.8× |

About 43% faster, and the waveforms are identical (0.995 correlation, same sample
count). On startup the server logs which device it got:

```
[kokoro] worker ready on mps
```

Force it with `HUIVER_DEVICE=cpu|mps|cuda` in `.env`. Anything unavailable falls back
to CPU rather than failing.

## What leaves your machine

Nothing you feed it. Book text is never uploaded — Kokoro is local torch inference,
and the generated audio is written straight to `data/`.

The one bit of outbound traffic is `huggingface_hub` downloading the Kokoro weights
(~317 MB into `~/.cache/huggingface`) plus a small file per voice on first use, and a
cache freshness check when a worker starts. That check is what prints:

```
Warning: You are sending unauthenticated requests to the HF Hub.
```

It means "downloading anonymously", not "uploading your data". HF telemetry is
disabled by default. To cut the network off completely once your voices are cached:

```bash
HUIVER_OFFLINE=1   # in .env
```

The two cloud engines (OpenAI, ElevenLabs) *would* send chapter text to their APIs —
that is what they are — but both stay disabled unless you add an API key.

## Speech engines

Engines are pluggable — see `src/server/tts/`. Each one implements the `TTSProvider`
interface in `tts/types.ts` and is registered in `tts/index.ts`.

| Engine | Status | Enabled by |
| --- | --- | --- |
| Kokoro 82M | local, default | the Python venv above |
| OpenAI TTS | untested | `OPENAI_API_KEY` in `.env` |
| ElevenLabs | untested | `ELEVENLABS_API_KEY` in `.env` |

The two cloud engines are wired up but have not been run against a live API key.
Unavailable engines show up greyed out in the UI with the reason why.

## How it works

```
upload → extract chapters → chunk to ~420 chars → TTS → concat → ffmpeg → mp3
```

- `src/server/extract.ts` — EPUB (zip → OPF → spine) and plain-text parsing. Chapter
  names come from the book's own table of contents (EPUB3 `nav` or EPUB2 NCX), since
  plenty of EPUBs have no `<h1>` and title every document after the book itself.
  Contents pages are detected by link density and dropped.
- `src/server/chunk.ts` — splits chapters on paragraph/sentence boundaries, since
  Kokoro truncates past ~510 phoneme tokens
- `src/server/tts/kokoro.ts` — talks JSON-lines over stdin/stdout to a persistent
  Python worker (`py/kokoro_worker.py`), so the model loads once per job, not per chapter
- `src/server/convert.ts` — serial job queue; a failed chapter doesn't sink the book,
  and interrupted jobs resume on restart
- `src/server/audio-routes.ts` — voice previews (disk-cached) and live chapter
  streaming, which pipes each rendered chunk through a single ffmpeg process to
  produce one continuous MP3 stream
- `src/server/tts/warm.ts` — keeps one worker alive between preview/stream requests
  so they don't each pay the model-load cost
- State lives in SQLite at `data/huiver.db`
